# Phase 1, plan 1: explicit native managed-package resolution

## Objective and scope

Deliver one end-to-end package-to-extension boundary toward OMK 2.0 without
activating breaking defaults in the current 1.5.10 release train. Existing
spec-kit governance remains authoritative. This plan is execution tracking only.

Use one immutable `DefaultPackageManager` construction option:
`packageManifestDialect: "omk" | "omk+pi"`. Omission preserves compatibility.
Do not add environment flags, settings, CLI switches or version-dependent logic.
Document the exact programmatic entry point actually supported; do not claim
session SDK propagation if that path is not implemented.

The default switch and runtime import boundary are later phase-2 work. Do not
remove Jiti or Bun aliases in this slice: local Pi packages can still resolve
after an alias is removed, so absence is not import rejection.

## Constraints

- Preserve all existing dirty work, particularly loader lifecycle changes.
- Back up touched existing files before editing; no resets or broad staging.
- No commits, pushes, installation, builds, provider calls or release actions.
- Keep package versions and dependency locks unchanged.
- Preserve path validation, authoritative `omk` precedence and existing diagnostics.
- Keep the module-size ratchet; do not widen its baseline.
- Retain copyright/license notices and unrelated same-publisher dependencies.
